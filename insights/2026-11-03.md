## 1. AICR 让 Kubernetes 对 Vera Rubin NVL72「开箱即用」：配方化固化调优配置，跨机架 NVLink 首测 745 GB/s

【快讯内容】
NVIDIA 发布 AICR 面向 Vera Rubin NVL72 的 Kubernetes 开箱配方：以可复用 recipe 固化调优配置、生成部署包并校验集群。验证基于 GPU Operator v26.7.0 + DRA 驱动 v0.5.0（系统镜像预装 arm64 开源内核驱动，故 Operator 禁用自带驱动），整卡分配暂不含 MIG；经 IMEX ComputeDomain 跨两机架多节点 NVLink 首测 NCCL all-reduce 达 744.71 GB/s。开源于 NVIDIA/aicr v1.0.0（Preview）。

【观点】
系统软件方向直接参考——正中「多芯片/多节点调度」与「GPU 驱动与固件」：Vera Rubin NVL72 带来新驱动分支（R615.23 开源 GPU 驱动）、arm64 系统镜像预装内核模块、DRA 动态资源分配等一连串新约束，AICR 把这些「调通一次」的配置沉淀为声明式 recipe + 部署包 + 集群校验，实质是把新硬件的 K8s 就绪从「专家手工拧」升级为「版本锁定、可复现、可 CI 的配方」，延续 10-08 追踪的 AICR v1.0（aicr-v1-0…·配置版本锁定/CI 签名溯源）演进为具体旗舰硬件的落地配方，对自研训练/推理平台适配下一代 GPU 的驱动—算子—调度链路有直接借鉴。网络方向直接参考——首测经 IMEX ComputeDomain 做跨两 NVL72 机架的多节点 NVLink all-reduce，744.71 GB/s busbw 直接反映 Rubin 代 NVLink/SuperNIC 互联域的集合通信能力；ComputeDomain 作为跨机架 NVLink 的编程抽象，是 AI 工厂东西向 fabric 在 K8s 上的调度入口，值得网络侧关注其与 RoCE/InfiniBand 的协同。嵌入式方向无直接——面向数据中心级 NVL72 机架，无端侧内容。（注：R615.23/v26.7.0/v0.5.0/744.71 GB/s 等出自官方博文经 hyper.ai/daily.dev/blockchain.news 交叉核对，具体以 NVIDIA/aicr v1.0.0 发行说明为准；K8s 版本下限等细节待官方页面核实。）

## 2. NVIDIA Attribution：把分布式故障从「满屏 NCCL 报错」收敛到单一根因节点，带证据链

【快讯内容】
NVIDIA 开源 Attribution 工具，联动日志、指标与调度器状态做分布式 AI 故障根因定位，输出结构化结果（结论/根因/受影响节点/佐证症状/证据链），而非止步于其他 rank 上的 NCCL 报错。示例：某节点 GPU 硬故障（XID 149）引发其余 rank 连锁 NCCL 错误，其过滤阶段解码出信号完整性问题、将 NCCL 报错归为佐证，最终把根因锁定到 node-02。

【观点】
系统软件方向直接参考——正中「运行时安全」与「系统级性能分析与优化」：大规模同步训练中一个硬件故障会在所有 rank 上激起连锁 NCCL 超时/报错，传统排障被海量次生告警淹没、难辨首因；Attribution 以「过滤—归因—证据链」范式把次生 NCCL 报错降级为佐证、将根因收敛到具体节点与具体 XID，本质是把 straggler/故障定位从人工翻日志升级为可自动化、可审计的结构化结论，对自研训练栈的断点续训决策、故障节点隔离与 SRE 自动化有直接价值，与 10-22~10-24 Minerva 可观测性、10-27 Mission Control 2.5 自主恢复形成「观测—归因—自愈」链条。网络方向直接参考——XID 149 信号完整性、跨 rank NCCL 集合通信故障本质是互联 fabric（NVLink/SuperNIC/东西向链路）的健康问题，Attribution 对链路级异常的根因定位契合「AI 工厂网络遥测」与故障域隔离。嵌入式方向间接——方法论对边缘集群多节点推理的故障归因有借鉴，但本文面向数据中心，无端侧产品。（注：XID 149/node-02/证据链索引等出自官方博文经 blockchain.news 与 Developer Forums topic 387840 交叉核对，具体以官方页面为准。）

## 3. NVIDIA Recovery：从日志/GPU 指标/调度信号自动检测中断，隔离故障节点并从检查点续跑

【快讯内容】
同日配套博文介绍 NVIDIA Recovery：从日志、GPU 指标与调度器信号自动检测训练中断，隔离涉事节点，并在健康算力上从检查点重启作业；可选调用 NVIDIA Attribution 做更深层根因诊断。面向大规模分布式训练的自动化韧性，减少人工值守与算力空转。

【观点】
系统软件方向直接参考——正中「多芯片/多节点调度」与「运行时安全」：长周期大规模训练的最大隐性成本是故障后的人工介入与 GPU 空转，Recovery 把「检测中断→隔离坏节点→健康算力上检查点续跑」做成自动闭环，并以可选挂接 Attribution 实现「先恢复、再深究根因」的分层策略，正是生产级训练平台所需的自愈能力。它与 10-27 Mission Control 2.5（把自主恢复从 Slurm 扩展到 K8s 的作业恢复+硬件恢复双服务）同属一条韧性主线，三者（本篇 Recovery + Attribution + Mission Control）共同指向「作业级重启→根因归因→双服务解耦自愈」的演进，对自研训练编排的断点续训、straggler 处置与检查点策略（参考此前 NVRx 异步检查点）有直接借鉴。网络方向间接参考——节点隔离作用于 GPU/互联域，故障节点下线/再承接需与 fabric 健康判定协同。嵌入式方向间接——自动检测—隔离—续跑思路对边缘训练/联邦场景有方法论借鉴，但本文面向数据中心集群，无端侧产品。（注：能力描述出自官方博文经 Developer Forums topic 387835 与 blockchain.news 交叉核对，具体以 NVIDIA Recovery 官方文档为准。）
