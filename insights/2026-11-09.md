## 1. NVIDIA NeMo「把智能体失败转成测试与 harness 修复」闭环：Relay 采 trace → Compass 挖失败模式 → Eval Author 生成 Harbor 评测 → 单点改 harness 带留出集对比，面向可验证的 agent 运行时演进

【快讯内容】
NVIDIA 技术博文（约 11-04）给出一套用 NeMo 工具链系统性改进智能体 harness 的闭环：①以 NeMo Relay 捕获智能体运行轨迹（trace），用 NeMo Compass 从中挖掘失败模式（错误工具调用、请求路由错配、违反 ETHOS.md 定义的行为约束）并归并为结构化问题清单；②用 NeMo Eval Author 为每个失败生成可复现的 Harbor 评测（把 bug 固化成回归测试）；③每次只对 harness 做一处定向改动（示例改 Hermes Agent 的 SOUL.md，类比系统提示），在开发/留出（held-out）集上对比"改前/改后"两臂、带过拟合防护（多次复核通过才接受）后再提交。示例运行在 OpenShell 运行时、经 build.nvidia.com 托管的 Nemotron 模型上，方法对任意开放 harness（FreeCAD/LangChain 例）通用。

【观点】
本篇核心落在系统软件方向——运行时安全（沙箱/进程隔离）与系统级性能分析/优化，具直接参考价值。关键是把智能体可靠性工程从"靠人读日志拍脑袋调提示词"升级为可度量、可回归、带防过拟合的工程闭环，可拆为三点方法论：①trace→失败清单→测试的"可观测性即测试资产"路径（Relay 采集 + Compass 聚类 + Eval Author 固化），本质是把智能体行为纳入与传统软件一致的 CI/回归纪律，杜绝"改好一个问题引入另一个回归"——对自研 Agent 栈（本地 LLM+多子代理+工具调用）的质量门禁有直接借鉴；②"每次只改一处 harness + 开发/留出集两臂对比"是对智能体调优最易踩的过拟合坑（在少数样例上把提示词调得过专）的直接防御，与经典 ML 的 train/dev/test 纪律同构、却落到了 agent harness 层；③失败分类（错误工具调用/路由错配/ETHOS.md 行为违规）与"带外可验证边界"的思路一脉——延续 10-23 Sentry（BlueField-4 带外策略执行）、11-05 AI Factory Operations Agent（Nemotron+OpenShell 沙箱）、11-07 Vera CPU 代理沙箱冷启动等运行时安全主线，本篇补齐"运行时如何被度量与收敛"的一环，构成「隔离执行 + 可验证边界 + 可回归改进」的 agent 运行时工程三角。嵌入式方向间接参考——方法论（失败即测试、单点改动对比）对安全关键边缘 agent 的在环验证有借鉴，但示例面向数据中心/云托管 Nemotron、端侧无直接产品，且 OpenShell/NemoClaw 仍属 alpha/早期预览（据第三方测评网关与推理时延尚不稳定）。网络方向无直接关联。注意：本篇为教程/方法论性质、非基准发布，无加速/准确率数字；发布日期（11-04）据第三方（explainx）转述、NVIDIA 原页未独立核实，以官方页面为准。
