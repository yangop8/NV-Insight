## 1. NVIDIA 教 Python 开发者用 GPUDirect Storage 把数据直读进显存

【快讯内容】
NVIDIA 技术博客以 KvikIO（cuFile 的 Python/C++ 封装）演示 GPUDirect Storage（GDS）：在 GDS 就绪系统上把 1GiB 文件绕过 CPU bounce buffer 直取入 CuPy 显存缓冲（H100 / CUDA 13.3 / cuFile 1.18 / 本地 NVMe）。关键是验证"加速路径确实走通"——设 CUFILE_STATS_LEVEL=3 后用 gds_stats 查进程计数，nvfs 计数为经 nvidia-fs 的加速 I/O、posix 计数为 CPU 暂存回退（实测 256 次操作全走 nvidia-fs）；并以 KVIKIO_COMPAT_MODE / CUFILE_FORCE_COMPAT_MODE 控制是否调用 cuFile 及走 POSIX 路径，GDS 仅对页对齐（4096 字节倍数）读生效、非对齐读被拆分。

【观点】
系统软件：直击"GPU 饿死/存储瓶颈"的落地操作手册——把此前 cuFile 开源（08-04 FMS）、cuObject/SCADA Server SDK（10-01）那条"GPU 侧存储控制"演进链下沉到最可操作的 Python 开发者视角，给出可复现的路径验证方法（gds_stats nvfs vs posix）与对齐/compat 坑点，对自研推理栈的权重/KV 冷启动加载、数据集预取、训练数据流水线减少 CPU 参与与 NUMA 惩罚有直接参考，是把"数十万 GPU 线程微秒级直取"从架构叙事变成工程 checklist。网络：GDS 属 GPUDirect Storage 家族，与 BlueField-4 STX 存储卸载、Spectrum-X 存储-网络融合、cuObject 的 RDMA 线协议同一数据面脉络，本文聚焦本地 NVMe 直取为支撑性背景，网络间接参考。嵌入式无直接参考价值。

> 参考文章：[How to Read Data into GPU Memory in Python with NVIDIA GPUDirect Storage](https://developer.nvidia.com/blog/how-to-read-data-into-gpu-memory-in-python-with-nvidia-gpudirect-storage/)

## 2. NVIDIA Sentry：在 BlueField-4 DPU 上做运行时 AI 智能体带外安全执行

【快讯内容】
GTC Berlin 发布的 OpenShell 参考架构技术版深挖其 Sentry 组件：Sentry 是监控 AI 智能体、对其访问模型/工具/数据执行策略的安全软件框架，基于 NVIDIA DOCA 构建、运行在 BlueField-4 DPU 上。核心是"策略执行与被监控的智能体工作负载分离"——执行点在智能体之外，被攻陷的智能体无法篡改自身约束（带外 out-of-band 执行），对需要更强防护的部署提供独立监控与在硅（in-silicon）执行。与 09-28 追踪的「Open Agent Safety Platform」总览属不同 URL——本篇为 Sentry 运行时执行机制的专题技术深潜。

【观点】
网络：又一则"DPU 作策略执行点"的落地——把智能体越界监控/阻断从主机 CPU 卸载到 BlueField-4 数据面、以 DOCA 为基座，契合零信任 AI 工厂东西向默认管控，与 09-01 SafeMind、03-23 Zero-Trust AI Factories、09-28 Open Agent Safety Platform 一脉，是 DPU 从网络/存储卸载扩展到"智能体安全卸载"的又一数据面应用。系统软件：带外执行独立于被监控进程、规避"让智能体自证清白"的自证悖论，为长时自主/多租户 agent 运行时提供可验证边界，可回灌 vLLM/SGLang 等推理栈的进程隔离与运行时准入控制，延续"harness 即可验证运行时"工程范式。嵌入式：硬件根信任的"越界即隔离"方法论对安全关键边缘 agent 部署有借鉴，但本篇面向数据中心 BlueField-4，端侧无直接产品，间接参考。

> 参考文章：[Inside NVIDIA Sentry: Secure AI Agents at Runtime](https://developer.nvidia.com/blog/inside-nvidia-sentry-secure-ai-agents-at-runtime/)

## 3. NVIDIA OpenShell 参考架构：规模化保障与治理 AI 智能体工作负载

【快讯内容】
GTC Berlin 发布的 OpenShell 参考架构技术版：OpenShell 是开源运行时，把智能体工作负载一律视作不可信、按需最小授权。架构含四组件——Gateway、Supervisor、Sandbox、Policy Prover；BlueField-4 上的 Sentry 为需要更强防护的部署追加独立带外监控与在硅执行。引 CoreWeave 在 NVIDIA Vera CPU 上实测：较主流 x86 CPU 沙箱启动快 3x+、智能体循环完成快 1.8x（厂商自报数据）。OpenShell 以 Apache 2.0 开源。

【观点】
系统软件：把此前零散的 OpenShell（Vera 内核级隔离沙箱）/Sentry（BlueField-4 带外监控）收敛为一套可规模化落地的参考架构——Gateway/Supervisor/Sandbox/Policy Prover 四件套 + 最小授权 + 可验证策略，给自主智能体运行时提供"默认不可信、按需授权、带外执行"的开箱范式，Apache 2.0 可移植可回灌自研推理/agent 栈的沙箱化与准入控制；Vera CPU 沙箱启动 3x+/循环 1.8x 把安全开销做进可接受区间，直击"安全拖慢智能体"的采纳顾虑。网络：Sentry 在 BlueField-4 做 in-silicon 执行，把安全策略执行点推到 DPU 数据面，是零信任 AI 工厂东西向管控的架构级样板，网络直接参考。嵌入式：内核级隔离 + 最小授权 + 策略分离的方法论对安全关键边缘 agent 有借鉴，但面向数据中心 Vera+BlueField-4，端侧无直接产品，间接参考。

> 参考文章：[How NVIDIA OpenShell Reference Architecture Secures and Governs AI Agent Workloads at Scale](https://developer.nvidia.com/blog/how-nvidia-openshell-reference-architecture-secures-and-governs-ai-agent-workloads-at-scale/)
